# 安全 Rust 与不安全 Rust 如何交互

## 翻译

安全 Rust 和不安全 Rust 之间是什么关系？它们如何交互？

安全 Rust 与不安全 Rust 的界限由 `unsafe` 关键字控制，它充当从一方通往另一方的接口。正因如此，我们才能说安全 Rust 是一门安全的语言：所有不安全的成分都被严格挡在不安全边界之外。如果你愿意，甚至可以在代码库中加入 `#![forbid(unsafe_code)]`，从静态层面保证你只写安全 Rust。

`unsafe` 关键字有两种用途：**声明编译器无法检查的契约的存在**，以及**声明程序员已检查过这些契约已被遵守**。

你可以用 `unsafe` 来表明函数和 trait 声明上存在未被检查的契约。在函数上，`unsafe` 意味着函数的**使用者**必须查阅函数文档，确保自己以维持该函数所要求契约的方式使用它。在 trait 声明上，`unsafe` 意味着 trait 的**实现者**必须查阅 trait 文档，确保自己的实现维持该 trait 所要求的契约。

你可以用 `unsafe` 标记代码块，声明块内执行的所有不安全操作都已验证遵守了那些操作的契约。例如，传给 `slice::get_unchecked` 的索引在界内。

你可以用 `unsafe` 标记 trait 实现，声明该实现遵守了 trait 的契约。例如，某个实现了 `Send` 的类型确实可以安全地移动到另一个线程。

标准库中有若干不安全函数，包括：

- `slice::get_unchecked`，执行未检查的索引，允许随意违反内存安全。
- `mem::transmute` 把某个值重新解释为给定类型，以任意方式绕过类型安全（详见 conversions）。
- 每个指向定长类型的裸指针都有 `offset` 方法，若传入的偏移量不"在界内"就会引发未定义行为。
- 所有 FFI（外部函数接口）函数调用都是 `unsafe` 的，因为另一种语言可能执行 Rust 编译器无法检查的任意操作。

截至 Rust 1.29.2，标准库定义了以下不安全 trait（还有别的，但尚未稳定，有些可能永远不会稳定）：

- `Send` 是一个标记 trait（没有 API 的 trait），承诺实现者可以安全地发送（移动）到另一个线程。
- `Sync` 是一个标记 trait，承诺线程可以通过共享引用安全地共享实现者。
- `GlobalAlloc` 允许自定义整个程序的内存分配器。

Rust 标准库的许多部分内部也使用了不安全 Rust。这些实现通常经过严格的人工检查，因此建立在这些实现之上的安全 Rust 接口可以认为是安全的。

需要这一切区分，归根结底源于安全 Rust 的一个基本属性，即**健全性属性**：

> 无论如何，安全 Rust 的客户端都无法引发未定义行为。

安全/不安全的划分设计意味着安全 Rust 与不安全 Rust 之间存在一种**不对称的信任关系**。安全 Rust 本质上必须信任它所接触的任何不安全 Rust 被正确编写。另一方面，不安全 Rust 不能不加小心地信任安全 Rust。它可以信任**自己是其客户端**的安全 Rust，但不能信任**由其客户端选择或提供**的安全 Rust。

举个例子，Rust 有 `PartialOrd` 和 `Ord` 两个 trait，用来区分"仅仅"可比较的类型和提供"全序"的类型（大体意思是比较行为合理）。

`BTreeMap` 对偏序类型其实没有意义，因此它要求键实现 `Ord`。然而，`BTreeMap` 的实现内部有不安全 Rust 代码。由于一个草率的 `Ord` 实现（写它是安全的）导致未定义行为是不可接受的，`BTreeMap` 中的不安全代码必须写得能抵御并非真正全序的 `Ord` 实现——尽管要求 `Ord` 的全部意义就在于此。

不安全 Rust 代码就是不能信任安全 Rust 代码被正确编写。话虽如此，如果你喂给它不具备全序的值，`BTreeMap` 仍会表现完全错乱。它只是永远不会引发未定义行为。

有人可能会问，既然 `BTreeMap` 不能信任 `Ord`（因为它是安全的），那它为什么能信任任何安全代码？例如 `BTreeMap` 依赖整数和切片被正确实现。那些也是安全的，对吧？

区别在于**范围**。当 `BTreeMap` 依赖整数和切片时，它依赖的是一个非常具体的实现。这是可衡量的风险，可以与收益权衡。这种情况下基本零风险；如果整数和切片坏了，所有人都坏了。而且它们与 `BTreeMap` 由同一批人维护，容易盯住。

跨 crate 边界也是如此。假设 crate `foo` 依赖 crate `bar`，那么 crate `foo` 中的不安全 Rust 可以信任 crate `bar` 中的安全 Rust。这是因为 crate `foo` 选择依赖 crate `bar`，从而信任 crate `bar` 被正确实现。

另一方面，`BTreeMap` 的键类型是泛型的。信任它的 `Ord` 实现意味着信任任意客户端的 `Ord` 实现。这里风险很高：某处某人会犯错搞砸他们的 `Ord` 实现，甚至只是因为"看起来能工作"就直白地谎称提供全序。当这种情况发生时，`BTreeMap` 需要有所准备。

同样的逻辑适用于信任传给你的闭包会正确行事。

这个**无界泛型信任**问题，正是不安全 trait 存在的原因。`BTreeMap` 类型理论上可以要求键实现一个叫 `UnsafeOrd` 的新 trait 而非 `Ord`，大致如下：

rust

```
use std::cmp::Ordering;

unsafe trait UnsafeOrd {
    fn cmp(&self, other: &Self) -> Ordering;
}
```



然后，类型会用 `unsafe` 来实现 `UnsafeOrd`，表明他们已确保自己的实现维持 trait 所期望的任何契约。在这种情况下，`BTreeMap` 内部的不安全 Rust 就有理由信任键类型的 `UnsafeOrd` 实现是正确的。如果不是，那是 unsafe trait 实现的错，这与 Rust 的安全保证一致。

是否将 trait 标记为 `unsafe` 是 API 设计选择。安全 trait 更容易实现，但任何依赖它的不安全代码必须防御错误行为。标记 trait 为 unsafe 把这一责任转移给实现者。Rust 传统上避免标记 trait 为 unsafe，因为这会使不安全 Rust 蔓延，这并不可取。

`Send` 和 `Sync` 被标记为 unsafe，因为线程安全是基本属性，不安全代码不可能像防御有 bug 的 `Ord` 实现那样防御它。类似地，`GlobalAlloc` 掌管程序中所有内存，以及建立在它之上的 `Box` 或 `Vec` 等其他东西。如果它做了奇怪的事（在内存仍在使用时把同一块内存给另一个请求），就没有机会检测并做任何事。

是否标记你自己的 trait 为 `unsafe` 取决于同类考量。如果不安全代码无法合理预期防御 trait 的损坏实现，那么标记该 trait 为 unsafe 是合理选择。

顺便说一句，虽然 `Send` 和 `Sync` 是不安全 trait，但当这种推导可证明安全时，它们也会自动为类型实现。`Send` 会自动为所有仅由实现了 `Send` 的类型值组成的类型推导。`Sync` 会自动为所有仅由实现了 `Sync` 的类型值组成的类型推导。这最小化了使这两个 trait 不安全所带来的蔓延性不安全。而且没多少人会实现内存分配器（或者说直接使用它们）。

这就是安全 Rust 与不安全 Rust 之间的平衡。这种区分旨在让使用安全 Rust 尽可能符合人体工程学，但在编写不安全 Rust 时需要额外努力和小心。本书余下部分主要讨论必须采取的那类小心，以及不安全 Rust 必须维持哪些契约。

## 要点提炼

1. **`unsafe` 是接口**，把不安全代码隔离在边界之后。安全 Rust 的保证是：安全代码不会引发 UB。
2. **两种用法**：
   - `unsafe fn` / `unsafe trait`：声明"存在编译器无法检查的契约"，责任在**调用者/实现者**。
   - `unsafe {}` / `unsafe impl`：声明"我已检查并遵守了契约"，责任在**写这段代码的人**。
3. **不对称信任**：安全代码必须信任它调用的不安全代码正确；不安全代码**不能**盲目信任它调用的安全代码（因为安全代码可能来自不可信的客户端）。
4. **`BTreeMap` 的例子**是核心：
   - 它依赖 `Ord`（安全 trait），但 `Ord` 的实现可能来自任意客户端，可能写错。
   - 因此 `BTreeMap` 内部的不安全代码必须写得**能抵御非全序的 `Ord` 实现**——只保证不 UB，不保证行为正确。
   - 它**可以**信任整数、切片（具体、同维护者、零风险），但**不能**信任泛型 `Ord`（无界风险）。
5. **`unsafe trait` 解决"无界泛型信任"**：把"实现必须正确"的责任从使用方转移到实现方。`UnsafeOrd` 若实现错误，是 `unsafe impl` 的错，符合 Rust 安全保证。
6. **何时标记 trait 为 unsafe**：如果不安全代码无法合理防御该 trait 的错误实现（如 `Send`/`Sync` 的线程安全、`GlobalAlloc` 的全局内存），就标 unsafe。否则优先安全 trait，避免不安全蔓延。
7. **`Send`/`Sync` 的自动推导**减轻了蔓延：组合类型自动继承，减少手动 `unsafe impl`。

这一页是 Nomicon 对"安全/不安全边界"的纲领性说明，和你做的 `tests5.rs` 直接对应：`unsafe fn` 上的 `# Safety` 文档 = 声明契约；`unsafe {}` 块里的注释 = 声明你遵守了契约。
